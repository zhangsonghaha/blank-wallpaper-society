## 一、审查背景

前两轮头脑风暴已识别 40+ 项功能（P0-P5），涵盖核心体验、安全合规、社区社交、商业化、工程质量等维度。task-backlog.md 显示所有 28 项开发任务已完成。第二轮中多项安全功能已实现（Altcha验证码、CSRF防护、账号注销、邮件服务）。

本轮分析聚焦于**前三轮未深入审视的维度**：
1. **基础设施与运维** — 部署、监控、容灾
2. **代码级安全风险** — 硬编码凭据、输入校验、SQL注入
3. **数据层问题** — 连接池、事务、索引优化
4. **运维可观测性** — 日志、监控、告警
5. **已实现功能的深度缺陷** — 功能"有"但不"完善"

## 二、全新发现的欠缺与风险

### 🔴 A. 代码级安全风险（极高风险 — 必须立即修复）

#### A3. 输入校验不完整 — XSS/注入风险
**现状：**
- 评论系统（`comments/route.ts`）未对用户输入做 HTML 转义/XSS 过滤
- 搜索接口直接拼接 LIKE 查询（虽有参数化，但无输入长度/格式限制）
- 用户昵称、简介等字段无 sanitization
- 全局无 DOMPurify 或类似 XSS 防护库
**建议：**
- 引入 `dompurify` 或 `sanitize-html` 对所有用户输入进行清洗
- API 层添加输入验证（长度限制、格式校验、危险字符过滤）
- 评论内容存储前转义 HTML 标签
- 设置 Content-Security-Policy 响应头
**影响：** 高 — 存储型 XSS 可导致账号劫持  
**工作量：** 中

#### A4. API Key 存储安全性
**现状：** `api_keys` 表使用 `key_hash` 索引，但需确认：
- API Key 原文是否在创建后立即丢弃（仅存储 hash）
- Key 生成是否使用密码学安全随机数
- 是否有 Key 轮换/吊销机制
**建议：**
- 确认 API Key 仅存储 hash，创建时一次性展示原文
- 添加 Key 自动过期和手动轮换功能
- Key 前缀显示（如 `sk_live_****xxxx`）便于识别
**影响：** 中 — API Key 泄露可导致资源滥用  
**工作量：** 小-中

---

### 🔴 B. 基础设施与运维（高风险）

#### B1. 无健康检查端点
**现状：** 无 `/health` 或 `/healthz` 端点
**影响：**
- 负载均衡器无法检测应用健康状态
- Kubernetes/容器编排无法做存活探针
- 运维无法快速判断服务是否正常
**建议：**
- 添加 `/api/health` 端点，检查：数据库连接、Redis 连接、MinIO 连接、内存使用率
- 区分 liveness（进程存活）和 readiness（服务就绪）
**工作量：** 小

#### B2. 无 Docker/容器化配置
**现状：** 无 Dockerfile、docker-compose.yml
**影响：**
- 开发环境不一致
- 部署流程不可复现
- 无法利用容器编排（K8s/ECS）
**建议：**
- 编写多阶段 Dockerfile（构建阶段 + 运行阶段）
- docker-compose.yml 包含 Next.js + MySQL + MinIO + Redis
- .dockerignore 排除 node_modules/.next
**工作量：** 中

#### B3. 无错误监控与告警
**现状：**
- 无 Sentry/Bugsnag/Datadog 等错误监控
- 仅 `console.error` 输出到服务器日志
- 无结构化日志（JSON format）
- 无日志聚合与分析
**建议：**
- 接入 Sentry（Next.js 有官方 SDK）
- 结构化日志输出（JSON 格式 + correlation ID）
- API 错误自动上报
- 前端 JS 错误自动上报
- 设置告警规则（错误率 > 阈值时通知）
**影响：** 高 — 生产环境中无法感知和定位问题  
**工作量：** 中

#### B4. 无数据库自动备份机制
**现状：** 无任何自动备份策略
**影响：** 数据丢失不可恢复
**建议：**
- Aliyun RDS 自动备份（已有，但需确认配置）
- 异地备份（跨区域）
- 备份恢复演练（定期验证备份可用性）
- 用户数据导出功能（GDPR 合规）— 已有 admin/export 但用户侧缺失
**影响：** 极高 — 数据丢失风险  
**工作量：** 小（RDS 配置）+ 中（用户侧导出）

#### B5. 无优雅关闭机制
**现状：** 无 SIGTERM/SIGINT 信号处理
**影响：** 部署更新时正在处理的请求会被中断
**建议：**
- 监听进程信号，停止接受新请求
- 等待进行中的请求完成（grace period）
- 关闭数据库连接池
- 关闭 Redis 连接
**工作量：** 小

### 🟡 C. 数据层与性能问题（中-高优先级）

#### C1. 数据库连接池配置过小
**现状：** `connectionLimit: 3`，`maxIdle: 1`
**问题：**
- 3 个连接对于生产环境明显不足
- 高并发时请求排队等待连接
- 每个 API 路由都直接 `await pool.query()`，无连接复用策略
**建议：**
- connectionLimit 提升到 10-20（根据 RDS 规格）
- maxIdle 设置为 connectionLimit 的 50%
- 添加连接池监控指标
- 考虑读操作使用只读副本（RDS 只读实例）
**影响：** 高 — 并发瓶颈  
**工作量：** 小

#### C2. 无数据库事务使用
**现状：** 代码库中无 `BEGIN`/`COMMIT`/`ROLLBACK`，无事务性操作
**问题：**
- 用户注册（创建用户 + 初始化等级 + 初始化通知设置）不是原子操作
- 删除图片（删除 favorites + comments + collection_images + image_tags + image）不是原子操作
- 收益提现（扣除余额 + 记录订单）不是原子操作
- 数据不一致风险
**建议：**
- 关键操作使用 `getConnection()` + `connection.beginTransaction()` + `commit()`/`rollback()`
- 至少覆盖：注册、删除图片、收益操作、支付流程
**影响：** 高 — 数据一致性风险  
**工作量：** 中

#### C3. 缺少关键数据库索引
**现状分析：** 当前索引覆盖较好，但以下查询可能缺失索引：
- `images` 表缺少 `user_id` 索引（查询用户的图片需要全表扫描）
- `images` 表缺少 `download_count/view_count` 排序索引
- `favorites` 表缺少联合索引 `(user_id, created_at)` 用于下载历史排序
- `download_logs` 表缺少 `user_id` 索引（查询用户下载历史）
**建议：**
- 添加缺失索引
- 使用 `EXPLAIN` 分析慢查询
- 考虑查询日志（RDS 慢查询日志）
**影响：** 中 — 随数据量增长性能劣化  
**工作量：** 小

#### C4. 限流存储仅用内存 Map
**现状：** `rate-limit.ts` 使用 `Map<string, RateLimitEntry>` 做限流
**问题：**
- 多实例部署时各实例限流独立，无法共享状态
- 进程重启后限流状态丢失
- 无法实现精确的全局限流
**建议：**
- 已有 `redis.ts`，应将限流数据迁移到 Redis
- 使用 Redis 的原子操作（INCR + EXPIRE）实现分布式限流
- 滑动窗口限流（更精确）
**影响：** 中 — 多实例部署时限流失效  
**工作量：** 中

#### C5. Redis 连接配置硬编码
**现状：** `redis.ts` 中 host/port/password 硬编码
**建议：** 同 A1，迁移到环境变量
**影响：** 中  
**工作量：** 小

### 🟡 D. 已实现功能的深度缺陷（中优先级）

#### D1. 暗黑模式虽已实现但可能不完整
**现状：** `layout.tsx` 已引入 `next-themes` ThemeProvider，但需验证：
- 所有页面是否有暗色 CSS 变量定义
- 管理后台是否支持暗黑模式
- 图片编辑器是否适配暗黑模式
- 第三方组件（如编辑器 Canvas）是否适配
**建议：** 全面测试暗黑模式下的 UI 一致性
**影响：** 中 — 暗黑模式体验断裂  
**工作量：** 中

#### D2. 批量上传仍未实现
**现状：** `UploadClient.tsx` 仍然只支持单文件上传，第二轮标记为 P2 但未开发
**建议：** 保持第二轮建议 — 多文件拖拽 + 批量进度 + 批量标签设置
**影响：** 高 — 创作者核心效率需求  
**工作量：** 中

#### D3. 测试覆盖极度不足
**现状：**
- `vitest.config.ts` 已配置，但仅有 1 个测试文件 `search-history.test.ts`
- 核心业务逻辑（支付、认证、NSFW检测、邮件）零测试覆盖
- 无 E2E 测试
- 无 API 集成测试
**建议：**
- 优先覆盖关键路径：认证流程、上传流程、支付流程
- 库文件单元测试（earnings.ts、user-level.ts、nsfw.ts）
- API 路由集成测试
- 逐步提升覆盖率目标：30% → 60% → 80%
**影响：** 高 — 重构和迭代无安全网  
**工作量：** 大（持续建设）

#### D4. NSFW 检测未集成到上传流程
**现状：** `nsfw.ts` 库已存在，但需确认是否在上传 API 中自动调用
**建议：**
- 上传 API 中集成 NSFW 自动检测
- 检测结果存入 images 表（nsfw_flagged, nsfw_score 字段已有索引）
- 超阈值图片自动标记为 pending 状态
**影响：** 高 — 内容安全防线  
**工作量：** 小-中

#### D5. 水印功能未被使用
**现状：** `watermark.ts` 库已存在，但水印文字硬编码为 "ImageGallery"
**问题：**
- 未在上传或展示流程中调用
- 水印文字应可配置（站点名称）
- 无管理后台水印开关
- 无水印位置/透明度配置
**建议：**
- 上传流程中可选添加水印
- 管理后台添加水印配置（开关/文字/位置/透明度）
- 展示缩略图可加水印，原图下载无水印
**影响：** 中 — 内容保护  
**工作量：** 中

#### D6. 视频壁纸组件存在但上传不支持
**现状：** `VideoWallpaper.tsx` 组件已存在，`media_type` 字段可能在数据库中，但上传路由（`upload/route.ts`）的 `ALLOWED_TYPES` 不包含 mp4/webm
**建议：**
- 上传路由支持视频文件类型
- 视频大小限制单独配置（如 50MB）
- 视频封面帧自动提取（使用 ffmpeg/sharp）
- 瀑布流中视频壁纸自动播放（静音循环）
**影响：** 中 — 差异化功能不可用  
**工作量：** 中-大

### 🟢 E. 运维可观测性与增长（中优先级）

#### E1. 无用户行为分析
**现状：** 无 Umami/PostHog/Google Analytics 等分析工具
**影响：** 无法量化用户行为，运营决策缺乏数据支撑
**建议：**
- 接入 Umami（自托管，隐私友好）或 PostHog
- 追踪关键事件：浏览、下载、注册、上传、收藏
- 管理后台 DashboardTab 增加行为分析面板
**工作量：** 中

#### E2. 无结构化日志体系
**现状：** 全部使用 `console.log/error/warn`，无日志级别、无结构化格式
**建议：**
- 引入轻量日志库（pino / winston）
- 结构化 JSON 日志输出
- 日志级别可配置（development: debug, production: info）
- 请求 ID 关联（correlation ID）
**工作量：** 中

#### E3. 无 API 请求日志中间件
**现状：** API 路由无统一的请求/响应日志
**影响：** 无法追踪 API 调用链、无法统计响应时间、无法排查问题
**建议：**
- middleware.ts 中添加请求日志
- 记录：请求方法、路径、状态码、响应时间、用户ID
- 慢请求告警（> 2s）
**工作量：** 小-中

#### E4. 用户存储配额无限制
**现状：** 上传无总存储配额限制
**风险：** 恶意用户可无限上传，消耗存储空间
**建议：**
- 按用户等级设置存储配额（普通用户 1GB，创作者 5GB）
- 上传前检查配额
- 管理后台可调整配额
**影响：** 中 — 存储成本控制  
**工作量：** 小-中

#### E5. 无用户数据导出功能（用户侧）
**现状：** 管理后台有 CSV 导出，但用户无法导出自己的数据
**合规要求：** GDPR/个人信息保护法要求用户可获取其个人数据
**建议：**
- 新增 `/api/user/export` 端点
- 导出内容：个人信息、上传的图片列表、收藏列表、下载历史
- 格式：ZIP（包含 JSON 数据文件 + 图片）
**影响：** 中 — 法律合规  
**工作量：** 中

### 🔵 F. 架构与技术债务（低-中优先级）

#### F1. 缺少 API 版本化策略
**现状：** V1 API 在 `/api/` 路径下，但无版本前缀（如 `/api/v1/`）
**风险：** API 变更会破坏现有客户端集成
**建议：**
- 新 API 使用 `/api/v2/` 前缀
- V1 API 保持兼容性
- 添加 API 弃用时间线
**工作量：** 中

#### F2. 无 Webhook 机制
**现状：** 无任何 Webhook 支持
**影响：** 外部系统无法实时响应平台事件
**建议：**
- 支持事件：图片审核通过、新用户注册、支付成功、评论新增
- 用户可配置 Webhook URL
- 签名验证（HMAC-SHA256）
- 失败重试机制
**工作量：** 中-大

#### F3. 内容安全策略（CSP）缺失
**现状：** 无 Content-Security-Policy 响应头
**建议：**
- 添加 CSP 头限制脚本来源
- 配置 `img-src` 允许 MinIO 域名
- 报告模式先观察（Content-Security-Policy-Report-Only）
**工作量：** 小-中

#### F4. 无 API 请求/响应 Schema 验证
**现状：** API 路由手动解析请求参数，无统一的 Schema 验证
**建议：**
- 引入 Zod 定义请求/响应 Schema
- 中间件层统一验证
- 自动生成 API 文档和类型
**工作量：** 中-大

## 五、建议实施路线图（第四版）

### 第一阶段：安全紧急修复（1-2 天）⚠️ 立即执行
1. 数据库/MinIO/Redis 凭据迁移到环境变量

## 六、关键发现总结

1. **凭据硬编码是最严重的安全问题**：数据库密码明文写在源代码中并提交到 Git，这是所有安全问题的根源。任何有代码访问权限的人都能直接连接生产数据库。这是本轮最重要的发现。

2. **数据库事务缺失是隐性炸弹**：注册、删除、支付等关键操作无事务保护，看似正常运行但数据一致性风险随时可能爆发。尤其是收益/支付相关操作，数据不一致会导致财务问题。

3. **已实现但未集成的功能是沉没成本**：NSFW 检测、水印、视频壁纸组件都已编写代码，但未集成到实际流程中。这些功能"有"但不"可用"，等于没有。

4. **运维可观测性几乎为零**：无错误监控、无结构化日志、无健康检查、无请求追踪。生产环境出问题时，只能靠用户反馈和手动翻日志。

5. **连接池配置是性能隐患**：3 个连接的生产配置在面对并发请求时将成为明显瓶颈，尤其是在图片列表+搜索+下载等高频操作场景下。

6. **限流架构不支持水平扩展**：基于内存 Map 的限流在单实例下可用，但一旦多实例部署则完全失效，而项目已有 Redis 连接却未利用。
